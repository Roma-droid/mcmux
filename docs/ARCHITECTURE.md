# Архитектура mcmux

## Слои

```
src/lib/versions.js       сравнение версий, эвристика java-тулчейна
src/lib/preprocessor.js   //? if/else препроцессор (версия + загрузчик)
src/lib/render.js         {{placeholder}} рендерер (строгий/нестрогий) + пути
src/lib/templates.js      рекурсивный обход директории шаблонов
src/lib/config.js         чтение/запись mcmux.config.json
src/lib/generate.js       материализация слоёв (init) и генерация цели (build)
src/commands/*.js         реализация подкоманд CLI
src/cli.js                разбор argv, диспетчер команд
templates/                исходный "шаблонный" код (common/fabric/forge/neoforge/root)
```

Никаких внешних npm-зависимостей — весь инструмент на голом Node.js API,
чтобы им можно было пользоваться без доступа в интернет и без риска, что
цепочка транзитивных зависимостей однажды сломается.

## Два прохода рендеринга

Между "исходным кодом мода в шаблонах инструмента" и "готовым Gradle-
проектом под конкретную версию" есть промежуточное состояние — исходники
внутри самого мод-проекта пользователя (`common/`, `fabric/`, ...). Это
сделано намеренно, в два прохода:

1. **`mcmux init` / `mcmux loader add`** (`materializeLayer` в
   `generate.js`) копирует `templates/common` и `templates/<loader>` из
   самого инструмента в проект пользователя, подставляя только
   **проектные** переменные — `modId`, `modName`, `modVersion`, `package`,
   `ModClass` — которые никогда не зависят от конкретной версии Minecraft
   или билда загрузчика. Если после этой подстановки в файле не осталось
   `{{...}}`, расширение `.tmpl` снимается и файл становится обычным
   `.java`-файлом — так пользователь сразу видит нормальный, читаемый
   исходник в IDE. Файлы, где остались {{плейсхолдеры}} (по факту —
   `build.gradle.kts.tmpl`, `fabric.mod.json.tmpl`, `mods.toml.tmpl`),
   которые содержат версии Minecraft/загрузчика, специально остаются
   шаблонами до момента, когда версия станет известна.

   Директивы препроцессора `//? if ... {` на этом шаге **не выполняются**
   — версия/загрузчик ещё не выбраны. Они остаются как есть в
   материализованных `.java`-файлах (это валидные `//`-комментарии, так
   что сами по себе такие файлы не ломают синтаксис, но и не являются
   финальным кодом — реальный `.java`, готовый к компиляции, появляется
   только на втором проходе).

2. **`mcmux generate` / `mcmux build`** (`generateTarget` в `generate.js`)
   берёт уже материализованные `common/` и `<loader>/` из проекта
   пользователя (не шаблоны инструмента!) для одной конкретной цели
   (`version` + `loader`), прогоняет каждый файл через препроцессор
   (`preprocess(source, {version, loader})`), и для файлов, всё ещё
   оканчивающихся на `.tmpl`, дорендеривает оставшиеся плейсхолдеры уже
   строгим рендерером (`renderTemplate` — бросает исключение, если
   что-то не подставилось: это защита от "забыли указать loaderVersion").
   Плюс всегда добавляется `settings.gradle.kts`, отрендеренный из
   `templates/root/` (это чистая обвязка сборки, никогда не редактируется
   пользователем, поэтому берётся прямо из шаблонов инструмента, а не из
   проекта).

Слой `<loader>` накладывается поверх слоя `common` — при совпадении
относительного пути loader-специфичный файл побеждает (в текущих
шаблонах пересечений путей нет: common содержит только код мода и
`IPlatformHelper`/`Services`, а loader — свой entrypoint, свою реализацию
`IPlatformHelper`, ресурсы и `build.gradle.kts`).

## Почему не Architectury / настоящий Stonecutter

Architectury Loom умеет компилировать один и тот же `common`-сорцсет
против нескольких загрузчиков за счёт сложной интеграции с самим Loom
(remap classes между mappings). Настоящий Stonecutter даёт то же самое для
версий через отдельный Gradle-плагин. Обе вещи требуют сетевого доступа к
конкретным Gradle Plugin Portal / Maven координатам и по-хорошему должны
быть протестированы реальной сборкой — в среде, где разрабатывался mcmux,
такой возможности не было (нет гарантированного доступа к
maven.minecraftforge.net / maven.fabricmc.net / maven.neoforged.net).

Поэтому mcmux выбирает более простую и более "проверяемую" стратегию:
вместо того, чтобы заставить один Gradle-проект уметь несколько
загрузчиков/версий одновременно (хрупко, версионно-чувствительно), он
**генерирует отдельный, совершенно обычный** Gradle-проект под каждую
пару (версия, загрузчик). Каждый такой проект — это именно то, что
document Fabric/Forge/NeoForge и так уже поддерживают "из коробки", без
какой-либо мультиплатформенной магии внутри самого Gradle-файла. Это
проще для понимания, проще для отладки (если один таргет не собирается,
остальные не затронуты) и не зависит от того, актуален ли на момент сборки
конкретный сторонний Gradle-плагин.

Идея деления на `common/` + loader-модули с `IPlatformHelper` через
`ServiceLoader` — это ровно тот же паттерн, что используют настоящие
"Multi-Loader Template" проекты в сообществе, просто без завязки на Loom
common-sourceset feature.
